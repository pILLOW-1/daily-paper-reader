## 摘要
经典查询优化搜索仅成本不同的代数等价计划。一旦LLM支持的算子加入，这一假设被打破：它们的位置、顺序和粒度共同决定了美元成本和答案质量，而不同方案之间的正确选择通常只有在运行时才能揭示。我们将这种设置形式化为智能体查询执行，这是一种将基于智能体的规划与执行交织在一起的查询执行范式，并且智能体工作流优化成为经典查询优化的类比。然后，我们提出了EnumGRPO，一种针对此设置的自我改进优化器。在学习阶段，EnumGRPO枚举涉及执行范式、算子类型、算子位置、选择性范围和投影宽度等决策的查询计划，然后通过上下文强化学习将质量-成本反馈提炼为可复用的规划启发式。在SWAN的四个数据库中，EnumGRPO以每个查询0.011美元的LLM算子成本实现了35.4%的执行准确率，与混合查询基线相比成本降低了约317倍，同时答案准确率相对提高了18%。

## Abstract
Classical query optimization searches over algebraically equivalent plans that differ only in cost. This assumption breaks once LLM-backed operators enter the picture: their placement, ordering, and granularity jointly determine both dollar cost and answer quality, and the right choice among the alternatives is often revealed only at runtime. We formalize this setting as agentic query execution, a query execution paradigm in which agent-based planning is interleaved with execution, and agent workflow optimization becomes the analogue of classical query optimization. We then present EnumGRPO, a self-improving optimizer for this setting. During a learning stage, EnumGRPO enumerates query plans over decisions such as execution paradigm, operator type, operator placement, selectivity scope, and projection width, then distills quality-cost feedback into reusable planning heuristics via in-context reinforcement learning. Across four databases in SWAN, EnumGRPO achieves 35.4% execution accuracy at $0.011 per query in LLM-operator cost, a ~317x cost reduction over the hybrid query baseline with an 18% relative improvement in answer accuracy.

## 1. 核心问题与整体含义（研究动机和背景）

**核心问题**：经典查询优化假设所有候选计划在代数上等价、仅成本不同，从而可以在编译时选择最优计划。然而，当大语言模型（LLM）支持的语义算子融入数据库后，该假设不再成立：
- LLM 算子是**近似**的：其输出质量取决于上下文、被处理的行数及计划中的放置位置。
- 每个 LLM 调用成本比关系算子高数个数量级。
- 因此，执行范式、算子类型、算子放置、选择性范围和投影宽度等结构化决策**共同决定了美元成本和答案质量**，且最优选择往往只有在运行时观察到中间结果后才能确定。

**整体含义**：该论文将这一新范式形式化为**智能体查询执行（Agentic Query Execution）**——一种将基于智能体的规划与执行交织在一起、根据中间结果动态选择下一步操作的执行方式。其对应的优化问题被称为**智能体工作流优化（Agent Workflow Optimization）**，是经典查询优化在LLM场景下的推广：从仅考虑成本的等价计划搜索，变为联合考虑质量与成本的动态计划搜索。

## 2. 方法论：核心思想、关键技术细节

### 核心思想
提出 **EnumGRPO**——一种自我改进的优化器，通过学习阶段的结构化枚举和上下文强化学习（In-Context Reinforcement Learning, ICRL），从质量-成本反馈中蒸馏出可复用的规划启发式，从而在查询时无需枚举即可做出更好的工作流决策。

### 关键技术细节

1. **规划空间（Plan Space）的五个正交轴**：
   - **执行范式（Execution Paradigm）**：数据驱动（逐行调用LLM） vs. 代码驱动（合成SQL规则）。
   - **算子类型（Operator Type）**：标量（逐行处理） vs. 聚合（批处理）。
   - **算子放置（Operator Placement）**：聚合前（pre-aggregation） vs. 聚合后（post-aggregation）。
   - **选择性范围（Selectivity Scope）**：全部（full） vs. 目标式（targeted，用SQL过滤后只对剩余行调用LLM）。
   - **投影宽度（Projection Width）**：窄（仅主键+目标列） vs. 宽（更多上下文字段）。

   每个轴都有经典查询优化的对应物（如谓词下推、延迟物化、访问路径选择），但此处同时影响质量和成本。

2. **EnumGRPO学习循环**（算法1）：
   - 每批处理B个查询。
   - 对每个查询，**PlanEnumerator** 生成N个不同的轴值赋值（保证多样性），作为软提示注入到智能体prompt中。
   - 并行执行N个rollout（每个对应一种计划），得到工作流轨迹。
   - 计算**多目标奖励**：结合执行准确率（EX）、元组级F1（TupleF1）、单元格级F1（CellF1）与归一化成本。
   - 计算**组内相对优势（Group-Relative Advantage）**：对每个查询组内的N个rollout，对奖励进行z-score归一化，得到每个轨迹的优势分数（同时分解为质量优势和成本优势）。
   - **经验蒸馏（Experience Distillation）** 四阶段流水线：
     - 阶段1：轨迹摘要（压缩为行为描述）。
     - 阶段2：对比分析（对比高/低优势计划，提出可推广的启发式）。
     - 阶段3：池更新（判断新启发式是新增、更新还是删除）。
     - 阶段4：批合并（去重并保持全局一致性）。
   - 最终经验池ε被注入到智能体的系统提示中，用于后续批次。

3. **运行时**：将学习到的经验池ε预置到智能体提示中，不进行枚举，智能体根据启发式逐步决策并执行自适应工作流。

4. **关键公式**：
   - 轨迹奖励：$G(\tau) = U(y;q,D) - \lambda \sum_t c(s_t, a_t)$
   - 复合质量分数：$r = w_{ex}·EX + w_{tuple}·TupleF1 + w_{cell}·CellF1$
   - 组内相对优势：$A_i = (r^*_i - \mu) / (\sigma + \delta)$

## 3. 实验设计

### 数据集与Benchmark
- **SWAN**：跨领域基准，包含120个“超出数据库知识”的问题，来自4个真实SQLite数据库（Bird的子集）：
  - California Schools（3个表，约3,870行/表）
  - European Football（8个表，约23,209行/表）
  - Formula One（14个表，约36,736行/表）
  - Superhero（10个表，约1,056行/表）
- 设置：移除了与问题相关的列和连接路径，使得系统必须借助LLM进行语义推理才能回答，而参考答案由原始数据库上的金SQL定义。
- 分割：随机40个查询用于EnumGRPO学习，80个用于评估。

### 对比方法
1. **Agentic Text2SQL**：智能体仅迭代优化和执行SQL，不调用显式LLM算子。
2. **Agentic BlendSQL**：智能体通过BlendSQL引擎执行混合查询，LLM算子作为内嵌成分。
3. **Agentic Query Execution（未优化）**：使用完整MCP工具集，包含独立语义算子，但无EnumGRPO。
4. **Agentic Query Execution w/ EnumGRPO（本文）**：在系统提示中添加了学习到的经验池。
5. **Agentic Query Execution w/ EnumGRPO (Held-out)**：仅使用非目标数据库的查询进行学习（测试跨模式迁移）。

### 评估指标
- 执行准确率（EX）、元组级F1、单元格级F1。
- 工作流效率：端到端延迟、LLM算子token消耗、美元成本。
- 可扩展性实验：将主实体表大小缩放到0.25×、0.5×、2×、4×。

## 4. 资源与算力

- **硬件**：Ubuntu 22.04服务器，双路Intel Xeon Platinum 8352Y（64核/128线程），504 GB RAM。**无GPU**，所有LLM推理通过云API端点完成。
- **LLM骨干**：规划使用Claude Sonnet 4.6（$3输入/$0.30缓存读/$15输出每百万token）；LLM算子使用Claude Haiku 4.5（$1输入/$0.10缓存读/$5输出每百万token）。

- **学习阶段成本**：约**\$41.2**（API调用）。
- **运行时成本（80个评估查询）**：EnumGRPO配置下LLM算子总成本约\$0.864（平均\$0.011/查询），相比Agentic BlendSQL（\$273.95）降低317倍。

## 6. 主要结论与发现

- **主要结果**：EnumGRPO在80个评估查询上达到**35.4%执行准确率**，高于Agentic BlendSQL（30.0%）和Agentic Text2SQL（19.2%）。同时将每个查询的LLM算子成本降至**\$0.011**，相比Agentic BlendSQL的\$3.42降低约**317倍**，相比未优化的Agentic Query Execution（\$0.039）降低**72%**。
- **LLM算子token消耗降低64.4%**（从52K/查询降至18K/查询）。
- **跨模式迁移**：Held-out实验表明经验池携带跨模式信号：准确率（32.9% vs 32.1%）相仿，但延迟和成本更低。
- **可扩展性**：当数据规模增大时，Agentic Query Execution（含EnumGRPO）的延迟和成本基本保持平坦，而Agentic BlendSQL呈线性增长。
- **经验池分析**：共学习到32个启发式，其中执行范式和选择性范围占主导（53%），说明这些是成本和质量的主要杠杆。

## 7. 优点

1. **问题形式化新颖**：首次将LLM算子的优化问题形式化为智能体工作流优化，明确了五轴规划空间，与经典查询优化形成类比，具有理论意义。
